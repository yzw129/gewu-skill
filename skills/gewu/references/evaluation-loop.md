# 蒸馏效果评估与 Skill 进化协议（v0.4）

## 为什么需要三段隔离

- **蒸馏集**：研究论文与人工审核的规则来源。
- **开发集 dev**：未参与蒸馏的研究场景，用于定位规则缺陷并修改行动流程。
- **测试集 test**：不参与蒸馏或版本选择；只对最终选定版本做一次性独立评价。

同一论文不得跨集合泄漏；如果没有足够独立数据，应如实报告探索性验证，避免“已证明成长”的表述。

## 配对对照实验

同一模型、版本、参数、任务问题和提供的上下文，唯一预定差异为系统提示词是否附加新 Skill。若使用不同模型、工具、温度、上下文或评估标准，实验不能直接归因于 Skill。

评价维度预先固定为：evidence、question、experiment、limitations，每项 1–5 分。人类评审不看组别（盲审包和映射分开保存），并保留评分者标识。答案可能暴露语言风格，所以盲法并非绝对。实际研究还应安排至少两位独立评审、评价一致性与分歧裁决。

## 评价结果

报告每维平均分差（Skill − Baseline）、逐题配对差、胜/负/平以及所有失败类型。只有综合、独立测试集结果能够支持“特定任务上的能力改善”结论。单次、少量题目不能证明普遍能力增长；报告效果范围、评分者数量、模型版本、提示词 SHA 和原始输入。

## 自我改进边界

- 只读取 dev 的人工评分报告；从实际失败任务提出具体触发条件、行动修正、失败原因假设。
- v0.4 evolve 的输出必须是新候选版本，不能覆盖原始已核查证据，也不能自动升级为正式版。
- 人工核对修改是否造成新错误；先在 dev 复测，再锁定最终版本。
- test 结果不得用于本轮继续调参；若根据 test 修改，需要建立新的独立测试集并记录污染。

## 实现限制

当前基准支持单评审逐案例打分和配对分析，不执行评分者一致性检验、统计显著性计算、自动问题生成或模型参数训练。API 执行需要用户明确同意上传任务及上下文。JSON 文件中仍可能包含敏感研究资料，应在项目内安全保管。
